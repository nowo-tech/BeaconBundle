## Environment variable

| Variable | Description |
|----------|-------------|
| `BEACON_DSN` | Full Beacon DSN. Empty string disables outbound reporting (1.25+: unless a [credentials provider](#credentials-provider-and-rotation-125) supplies a DSN; it stays the fallback). |
| `BEACON_RELEASE` | Optional app/code version string (wire via `release`). |
| `BEACON_WORKER_KEY` | Optional worker key (`bwk_…`) for [remote Messenger commands](USAGE.md#remote-retry-from-beacon) (1.16+); only on hosts that run workers. Secret: never commit it. |

## DSN format

```text
{scheme}://{public_key}:{secret}@{host}[:{port}]/{project_id}
```

`project_id` accepts a positive numeric legacy id **or** a canonical project UUID.

Examples:

```env
# Local Symfony Beacon over HTTPS (secret required) — numeric legacy id
BEACON_DSN=https://PUBLIC:SECRET@localhost:9444/1

# Same host with project UUID (preferred in current Symfony Beacon UI)
BEACON_DSN=https://PUBLIC:SECRET@localhost:9447/019fea2d-507b-7890-8b33-ca488db6f696

# Production subdomain
BEACON_DSN=https://PUBLIC:SECRET@errors.example.com/7

# Docker client → Beacon HTTP ingest on the host
BEACON_DSN=http://PUBLIC:SECRET@host.docker.internal:9081/2
```

Symfony Beacon rejects public-key-only authentication when the API key has a secret (all keys generated by Beacon include one).

## YAML reference

```yaml
nowo_beacon:
    enabled: true
    dsn: '%env(string:default::BEACON_DSN)%'
    environment: '%kernel.environment%'
    release: '%env(string:default::BEACON_RELEASE)%'
    server_name: null
    verify_peer: true
    timeout: 5.0
    ingest_paths: auto   # auto | versioned | legacy
    credentials_provider: null         # 1.25+: service id of a BeaconCredentialsProviderInterface (null = config only)
    credentials_cache_ttl: 60          # 1.25+: seconds a provider answer is reused (0 … 3600)
    credentials_allowed_origins: []    # 1.25.1+: origins a provider DSN may target (plus the origin of dsn)
    instance_settings_bridge: false    # 1.25+: DSN / worker key in the "beacon" InstanceSettings section
    transport:
        mode: sync   # sync | async | messenger
        retry:       # Beacon answered 5xx → wait and retry (0 retries = off)
            max_retries: 2
            delay_ms: 500
            multiplier: 2.0
            max_delay_ms: 5000
            jitter: 0.1
            status_codes: [500, 502, 503, 504]
    register_error_listener: true
    register_console_listener: true
    register_messenger_listener: true
    register_fatal_handler: true
    register_php_warning_handler: true
    php_warning_handler:
        continue: true
        capture_silenced: false
        # levels: []  # empty = warning+notice (no deprecations)
    include_scheduler_context: true
    messenger:
        transactions: false
        transaction_sample_rate: 1.0
        report_retries: false
        report_recovered: false
        retry_sample_rate: 1.0
        worker_memory_warning_ratio: null   # e.g. 0.8
        failure_transports: ['failed']
        trace_middleware:                  # 1.22+: Messenger trace correlation
            enabled: true                  # false = no bus gets BeaconTraceMiddleware
            buses: ['messenger.bus.default']
        remote_retry:                      # Retry / discard from the Beacon UI (1.16+), off by default
            enabled: false
            worker_key: '%env(default::BEACON_WORKER_KEY)%'   # bwk_…, required when enabled (unless a credentials provider supplies it)
            allowed_actions: [retry, discard]
            failure_transports: []         # empty = messenger.failure_transports
            poll_interval: 30              # seconds, 10 … 600
            poll_in_workers: true
    scheduler:
        check_ins:
            enabled: false                 # Scheduler check-ins (1.15+), needs symfony/scheduler
            max_runtime: {}                # e.g. { 'app:reports:nightly': 1800, App\Message\SyncCatalog: 600 }
            ignore: []                     # message FQCNs or command names
            descriptions: {}               # 1.16+: e.g. { 'app:reports:nightly': 'Builds the nightly sales report.' }
            catalog_refresh_hours: 24
    auto_http_transaction: false
    http_transaction_sample_rate: 1.0  # 1.17+: fraction of HTTP requests that send a transaction
    ignore_routes: []                  # 1.17+: route-name prefixes without HTTP transaction, e.g. [ingest_, api_poll_]
    before_send: null
    instrumentation:
        doctrine: false
        http_client: false
    ignore_exceptions: []
    ignore_http_client_errors: false   # 1.20+: listener also skips HttpExceptionInterface with status < 500
    ignore_paths:
        - '/_profiler'
        - '/_wdt'
        - '/build'
        - '/assets'
        - '/health'
        - '/.well-known/appspecific/com.chrome.devtools.json'
    monolog_handler:
        enabled: false
        level: error
        ignore_exceptions: []            # 1.20+: extra FQCNs, on top of the main ignore_exceptions
        ignore_http_client_errors: true  # 1.20+: skip HttpExceptionInterface with status < 500
    send:
        environment: true
        release: true
        server_name: true
        stacktrace: true
        request: true
        user: false
        runtime: true
        framework: true
        os: true
        client: false
```

The import file only points at the loader; route names (`nowo_beacon_self_test`, `nowo_beacon_self_test_trigger`) are stable.

## Credentials provider and rotation (1.25+)

Besides `BEACON_DSN` / `BEACON_WORKER_KEY`, the DSN and the worker key can come from a database record (owner decision
2026-11-10, Beacon request D-20261112-14), to rotate them without a deploy.

| Key | Default | Description |
|-----|---------|-------------|
| `credentials_provider` | `null` | Service id of a `Nowo\BeaconBundle\Credentials\BeaconCredentialsProviderInterface`. `null`: configuration only, exactly as 1.24 (same services, same arguments; proven by `DefaultWiringEquivalenceTest`). Checked at compile time (service exists and implements the port). |
| `credentials_cache_ttl` | `60` | Seconds a provider answer is reused (0 … 3600; 0 = read on every use). |
| `credentials_allowed_origins` | `[]` | 1.25.1+: origins (`scheme://host[:port]`, written exactly as in the DSN: `https://beacon.example.com` and `https://beacon.example.com:443` differ) a provider DSN may target. The origin of `dsn` is always allowed. Empty and no configured DSN: every provider DSN is refused. Lower-cased, trailing `/` removed; paths and credentials are rejected. |
| `instance_settings_bridge` | `false` | Registers the `beacon` InstanceSettings section, `nowo_beacon.credentials_provider.instance_settings` (provider + store) and a `SettingsChangedEvent` listener; becomes the provider when `credentials_provider` is null. Requires `nowo-tech/instance-settings-bundle`. |

**Resolution (runtime, never at compile time).** For each value, the provider's wins; a missing, invalid or
unreadable provider value falls back to the configured one; neither: reporting is off (events dropped, as with an
empty DSN). With a provider, an empty `BEACON_DSN` no longer disables the bundle at compile time: the listeners are
registered and the client decides per event.

- **Boot time uses the configuration.** The provider is read only after the first `kernel.request`,
  `console.command` or Messenger `WorkerStartedEvent`, so an error raised while the kernel boots is reported with
  `BEACON_DSN` and never waits for a database.
- **Failures never throw.** A provider exception is logged once (exception class only, never its message) until a read
  succeeds again; invalid values are logged once (reason only). A call made while the provider is being read (e.g. its
  own logging reaching the Monolog handler) gets the last snapshot or the configuration, never a nested read.
- **Cache.** `credentials_cache_ttl` seconds, then re-read. `kernel.reset` and `SettingsChangedEvent` (section `beacon`)
  only make it expire now; correctness never depends on the resetter (FrankenPHP worker with `kernel reset false`).
  Messenger resets services after each message, so a consumer re-reads the provider once per message.
- **Change.** When any effective value changes, the client, its transport, its async queue (pending requests are
  completed first) and the Messenger handler transport are rebuilt; remote-command calls and signature checks read the
  credentials on every call.

**Allowed origins (1.25.1, owner decision 2026-11-12).** A provider DSN, current or previous, is used only when its
origin is in `credentials_allowed_origins` or is the origin of `nowo_beacon.dsn`; otherwise it is ignored with one
warning (naming the origin, never a secret) and the configured DSN is used. The rotate command refuses a new DSN
outside the list.

**Pairing (audit NS-M1).** The configured worker key is used with a provider DSN only when that DSN has the same
origin (scheme, host, port) as `nowo_beacon.dsn`; otherwise there is no worker key (remote commands off, one warning)
until the provider also returns one. The same rule applies to the previous worker key. Keep `nowo_beacon.dsn` on the
same Beacon and project as the stored DSN.

**Rotation (current + previous with expiry).** A record can carry the value a rotation replaced, with an expiry
(ISO 8601). A previous value without an expiry, or expiring more than 30 days ahead, is ignored; a previous DSN must
target the same origin and project as the current one. Once the previous DSN is rejected too, it is not tried again
until the credentials change.

- DSN: events are sent with the current DSN. On HTTP 401 the same Envelope is re-sent **once** with the previous DSN
  while it has not expired; without one, the provider is re-read once (at most every 5 s) and, when the DSN changed, the
  Envelope is re-sent once with the new DSN. Otherwise the 401 stands. A warning names the step (never a key).
- Worker key: command signatures made with the previous key are accepted until its expiry; a claim / result answered
  with 401 is retried once with the previous key (or the re-read key). Works with one active key too (Beacon accepts
  the new key once it knows it).
- `nowo:beacon:credentials:rotate --dsn|--worker-key [--grace=86400]`: see [USAGE](USAGE.md#credentials-from-a-database-and-rotation-125).

## Ingest paths (versioned, legacy fallback)

Beacon 1.147 serves versioned canonical ingest paths (decision D-20261110-04) and keeps the unversioned paths as
permanent aliases:

| Call | Versioned (canonical, Beacon ≥ 1.147) | Legacy (every Beacon) |
| --- | --- | --- |
| Envelope | `POST {origin}/api/ingest/v1/{projectId}/envelope/` | `POST {origin}/api/{projectId}/envelope/` |
| Remote commands claim | `POST {origin}/api/ingest/v1/{projectId}/messenger/commands/claim` | `POST {origin}/api/{projectId}/messenger/commands/claim` |
| Remote command result | `POST {origin}/api/ingest/v1/{projectId}/messenger/commands/{id}/result` | `POST {origin}/api/{projectId}/messenger/commands/{id}/result` |

Same authentication, limits and answers on both. With `ingest_paths: auto` (default) the bundle works against any
Beacon version:

- A call to a Beacon target (origin + project id) goes to the versioned path unless the target is known to serve the
  legacy paths only.
- HTTP **404 or 405** there (an older Beacon has no such route): the same request is sent **once** more to the legacy
  path. The 404 that triggered the retry is not logged. A 404 / 405 means nothing was processed, so this never
  duplicates a request.
- The answer is remembered per target (`IngestPathResolver`, shared by the Envelope transports, remote commands and
  `nowo:beacon:test`); the newest answer replaces the older one:

  | Answer | Learned | Re-sent to the legacy path |
  | --- | --- | --- |
  | versioned 2xx, or a Beacon 400 / 401 / 403 / 413 / 415 / 422 | versioned | no |
  | versioned 404 / 405 | (forgotten if it was versioned: self-heal) | once |
  | versioned 408 / 429 / 5xx / any other status, or a network failure | nothing (the next call probes again) | no |
  | legacy 2xx, or a Beacon 400 / 401 / 403 / 413 / 415 / 422 | legacy | — |
  | legacy 404 / 405 too (unknown project or command) | versioned | — |
  | legacy 408 / 429 / 5xx / other, or a network failure | nothing | — |

  A transient 503 from a proxy or a load balancer in front of an older Beacon therefore never pins the versioned path,
  and a target known as versioned that starts answering 404 (Beacon downgrade, a remote-command `not_found` on both
  paths) heals itself on the next call. The project id in the key keeps an unknown project from pinning the versioned
  path for other projects or tenants on the same older Beacon.
- **No other status is re-sent** by this logic (429 and 5xx keep their usual handling, retries of the retrying HTTP
  client included), and a network failure (no HTTP answer) is neither re-sent nor remembered.
- `async` mode keeps a reference to the body of each pending versioned request (at most 100 pending requests) and does
  the legacy retry at flush.
- Log records carry the URL actually used (`url` context: versioned or legacy).

Worker mode (FrankenPHP without kernel reset): the remembered map only holds a server capability (origin + project id
→ versioned or legacy), never keys, secrets, request, user or tenant data. It is bounded to 32 targets
(`MAX_ENTRIES`), lives for the process and is intentionally **not** tagged `kernel.reset`, so a long-running worker or
Messenger consumer probes an older Beacon once (again only after a transient error or a self-heal).

Cost against Beacon < 1.147: one extra 404 per probe. Under **PHP-FPM** (one container per request) and for short
console commands, every request or run that sends something probes again: set `ingest_paths: legacy` until Beacon is
1.147, then remove it.

Use `ingest_paths: versioned` once every Beacon you send to runs 1.147 or later, or `legacy` to keep the previous
paths (for example behind a proxy that only allows them).

## Timeout hierarchy (REQ-RUNTIME-001)

Outbound Envelope ingest uses Symfony HttpClient with `timeout` / `max_duration` from `nowo_beacon.timeout` (default **5.0** seconds). Under FrankenPHP / FPM, keep:

**operation timeout (Beacon HTTP) &lt; PHP request budget &lt; Caddy / reverse-proxy write timeout**

so the bundle deadline fires first, the transport fails soft (log + `false`), and the worker thread is released. Demo Caddy/PHP budgets: [PERFORMANCE.md](PERFORMANCE.md#timeout-hierarchy) and [DEMO-FRANKENPHP.md](DEMO-FRANKENPHP.md#timeout-hierarchy-req-runtime-001).

When raising `timeout`, raise PHP `max_execution_time` and Caddy `servers.timeouts.write` in the **same** change.

## Retries on Beacon server errors

When Beacon answers an Envelope POST with a server error (`transport.retry.status_codes`, default 500 / 502 / 503 / 504), the bundle waits and sends the same Envelope again, up to `transport.retry.max_retries` times. The wait grows with each attempt — `delay_ms` × `multiplier`ⁿ, bounded by `max_delay_ms` and varied by `jitter` — and a `Retry-After` header from Beacon takes precedence. Only the last response is logged (`Beacon ingest rejected envelope.`).

- Not retried: 4xx responses and transport errors (DNS, refused connection, timeout) — a Beacon that is down does not multiply the time spent per send.
- Safe to repeat: Beacon stores one event per `event_id` and project, so a retry after a 500 that was in fact stored does not duplicate the event.
- Long `Retry-After` in `sync` mode: a synchronous send never waits longer than `max_delay_ms` for one retry. When `Retry-After` asks for more (for example a 503 with `Retry-After: 300`), the send is not retried — it returns at once and the rejection is logged — so a struggling Beacon cannot stall the request or worker thread. A `Retry-After` within the bound is honoured. `max_delay_ms: 0` removes the bound (and waits for any `Retry-After`). In `async` and `messenger` mode a `Retry-After` above `max_delay_ms` is still honoured, but every wait also counts against the request's idle `timeout`: a wait longer than `timeout` ends the send with an idle-timeout error, so a background send holds the worker (or the `kernel.terminate` phase) for at most about (`max_retries` + 1) × `timeout`. Note that `transport.mode: messenger` without a transport routing for `SendBeaconEnvelopeMessage` sends inline in the request, with this background behaviour.
- Where the wait happens: in `sync` mode inside the request that reports; in `async` mode on `kernel.terminate` / `console.terminate` (after the response is sent); in `messenger` mode in the worker. Worst case per send: (`max_retries` + 1) × `timeout` for the attempts plus `max_retries` waits, each at most `max_delay_ms` (a backoff or an honoured `Retry-After`) and at most `timeout`; with the defaults (`timeout` 5 s, 2 retries, `max_delay_ms` 5000) that is under 25 s, and 15 s + 1.5 s when Beacon sends no `Retry-After`. In `sync` mode under FrankenPHP / FPM keep that sum inside the [timeout hierarchy](#timeout-hierarchy-req-runtime-001), or lower `max_retries`.

Built with Symfony's `RetryableHttpClient` + `GenericRetryStrategy` around `http_client` (service `nowo.beacon.ingest_http_client` for `async` / `messenger`, `nowo.beacon.ingest_http_client.sync` with the bounded `Retry-After` for `sync`), used only for Envelope ingest; `nowo:beacon:test` and remote Messenger commands keep the plain client.

### `send.*` context switches

Each flag controls whether that category is attached to outbound events:

| Key | Default | Sent when enabled |
|-----|---------|-------------------|
| `send.environment` | `true` | `environment` |
| `send.release` | `true` | `release` (if configured) |
| `send.server_name` | `true` | `server_name` |
| `send.stacktrace` | `true` | Exception frames + `culprit`; for `captureMessage()` also a current PHP stacktrace (BeaconBundle frames filtered out). When files are readable, frames include `abs_path` and source context (`pre_context` / `context_line` / `post_context`, ≈5 lines). Enable `send.stack_vars` for `vars` (call arguments). |
| `send.request` | `true` | `request` + `contexts.request` (url, method, query, safe headers such as Host/User-Agent; secret-like query parameters such as `token` / `password` / `api_key` and URL credentials such as login-link `hash`, `signature` / `sig` and OAuth `code` are sent as `[Filtered]`) and `extra.request_*` when an HTTP request is available. Automatic HTTP exceptions also get nested `extra.http` (`route`, `controller`, `status_code`, `query_keys`). |
| `send.user` | `false` | Authenticated user summary (`id` / `username` / `email` when available). **May include PII** — keep off unless your privacy policy allows it. |
| `send.runtime` | `true` | `contexts.runtime` (PHP version) |
| `send.framework` | `true` | `contexts.framework` (Symfony version when available) |
| `send.os` | `true` | `contexts.os` |
| `send.client` | `false` | On HTTP exception events, attach `extra.http.client` (`ip` / `user_agent`). **May include PII** — off by default. |
| `send.stack_vars` | `false` | Attach function **argument** summaries as Sentry-compatible `frame.vars` (parameter names via reflection when possible). **May include PII** — off by default. Requires `send.stacktrace`. Values are size-capped and passed through sensitive-key redaction. Hosts with `zend.exception_ignore_args=1` omit exception-frame arguments (PHP default in some builds). |

Timestamps (`timestamp` fractional Unix + `datetime` ISO-8601 UTC with microseconds) are always sent. Correlation ids (`extra.trace_id` / tag `trace_id`) are always attached when the client is enabled.

Example — diagnostics without request URLs or user identity:

```yaml
nowo_beacon:
    send:
        request: false
        user: false
        client: false
```

## Important behavior

- Empty `dsn` means the bundle wires `NullBeaconClient`.
- `ignore_exceptions` only affects the automatic listeners and the Monolog handler. Manual `captureException()` calls still send unless your own code avoids them.
- `ignore_paths` only affects the HTTP exception listener and `auto_http_transaction`. Console / Messenger listeners are unaffected.
- `ignore_routes` and `http_transaction_sample_rate` only affect `auto_http_transaction`; exceptions on those routes are still reported.
- `monolog_handler` applies the same ignore rule as the listeners (`Support\IgnoredException`): the main `ignore_exceptions`, plus `monolog_handler.ignore_exceptions`, plus HTTP 4xx when `monolog_handler.ignore_http_client_errors` is true. Only Beacon skips the record; it still bubbles to the other handlers. Records without `context.exception` are forwarded as messages as before.
- `monolog_handler` never forwards the bundle transport's own logs (context flag `nowo_beacon_transport`, `EnvelopeTransport::LOG_CONTEXT_FLAG`): reporting a failed send through the same transport would loop while the receiver is down. Other handlers still receive them.
- `timeout` applies to the synchronous HTTP request path.
- `verify_peer: false` also disables host verification in the underlying HTTP client and should stay limited to local dev.
- Enabling `send.user` or `send.client` transmits identifiers that may be personal data; align with GDPR / privacy policy and legal pages on the Beacon UI.
- `register_fatal_handler: false` skips shutdown capture of fatal PHP errors.
- `register_php_warning_handler: false` skips the PHP warning interceptor (Symfony ErrorHandler / Monolog alone).

## Development with self-signed certificates

```yaml
when@dev:
    nowo_beacon:
        verify_peer: false
```

Do **not** disable peer verification in production.
